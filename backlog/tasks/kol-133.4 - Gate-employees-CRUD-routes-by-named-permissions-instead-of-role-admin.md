## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Resolves KOL-95. Now that the admin role is a normal, editable role (KOL-133.3) rather than a permanently-protected one, gating the employees route group by role:admin middleware is unsafe: an organization could edit the admin role's permissions and unknowingly change who can reach these routes, since middleware checks the role name, not the permission set.

Convert the employees resource routes (routes/web.php), including toggle-active and export, from role:admin middleware to named Spatie permissions following RoleSeeder's Verb:Resource convention (e.g. View:Employee, Manage:Employee), and grant those permissions to the admin role by default so existing behavior is unchanged for current admins.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Split the employees resource routes out of the shared role:admin group in routes/web.php into two permission-gated groups: View:Employee (index, show) and Manage:Employee (create, store, edit, update, destroy, toggle-active, export).
2. Add View:Employee and Manage:Employee to RoleSeeder's ADMIN_PERMISSIONS so admin keeps current access.
3. Write Pest feature tests: access granted via View:Employee/Manage:Employee without the admin role, and access denied (403) without the permission, for index/show/store/update/destroy/toggle-active/export.
4. Run pint --dirty and the new/affected test file(s).
5. Filed KOL-133.6 as a follow-up for the auth.isAdmin employee-link frontend drift (out of scope here, confirmed with user).
