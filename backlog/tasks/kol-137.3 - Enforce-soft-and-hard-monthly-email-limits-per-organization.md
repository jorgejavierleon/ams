## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Builds on KOL-137.1 (tracked volume) and KOL-137.2 (configured soft/hard limits). This slice wires the two thresholds to actual behavior.

- **Soft limit**: when an organization's email count for the current calendar month reaches its soft limit, notify platform admins (surfacing it in the SaaS panel is sufficient; a separate email to platform admins is not required). Fire the alert once per organization per month when the threshold is first crossed, not on every subsequent send.
- **Hard limit**: when an organization's count reaches its hard limit, every further send attempt for that organization in the same calendar month is suppressed instead of dispatched — no exceptions for any mail type, per the decision in KOL-137. Also notify platform admins once per crossing.
- Suppression is scoped strictly to the calendar month: it lifts automatically at the start of the next month, and a platform admin raising the hard limit mid-month un-blocks sending immediately without waiting for rollover.
- A suppressed send must fail silently from the end user's perspective (no 500s, no queued-job failures) — the triggering action in the app should complete normally even though its email didn't go out.

## User stories for manual testing (Gherkin)

```gherkin
Feature: Enforce organization email limits

  Scenario: Crossing the soft limit alerts platform admins without affecting sending
    Given organization "Acme" has a soft limit of 50 and has sent 49 emails this month
    When the 50th email for Acme is sent this calendar month
    Then a platform admin can see that Acme crossed its soft limit
    And Acme's emails continue to send normally

  Scenario: Crossing the hard limit blocks further sends
    Given organization "Acme" has a hard limit of 80 and has sent 80 emails this month
    When the app attempts to send another email on behalf of Acme this month
    Then the email is not sent
    And a platform admin can see that Acme hit its hard limit
    And the user-facing action that triggered the email still completes without error

  Scenario: Sending resumes automatically the following month
    Given organization "Acme" hit its hard limit in September
    When October begins and a new email is triggered for Acme
    Then the email sends normally

  Scenario: Raising the hard limit unblocks sending immediately
    Given organization "Acme" is currently blocked after hitting its hard limit of 80 this month
    When a platform admin raises Acme's hard limit to 100
    Then the next email triggered for Acme this month sends successfully
```

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. New email_limit_crossings table (org_id, type soft|hard, month, unique per org/type/month) as the once-per-crossing dedup + platform-admin-visible alert.
2. Organization: emailLimitCrossings() relation, emailSendsCountForMonth(), hasCrossedEmailLimitThisMonth(), recordEmailLimitCrossing() (firstOrCreate, idempotent).
3. New listener SuppressEmailOverHardLimit on MessageSending (fires before transport, can return false to cancel send) - suppresses when count >= hardLimit, unless hardLimit <= 0 (baseline unset = not configured, never suppress).
4. Extend RecordEmailSend (MessageSent) to also raise the soft-limit crossing once count >= softLimit, after recording the EmailSend.
5. OrganizationController::edit exposes softLimitCrossedThisMonth/hardLimitCrossedThisMonth; edit.tsx shows a destructive Alert for hard, a default Alert for soft (hidden if hard is also showing).
6. Pest: EmailLimitEnforcementTest covers soft alert-once, hard suppression + alert-once, raising override mid-month, month rollover, zero-limit-means-unconfigured, cross-org isolation.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Decision confirmed with user: a soft/hard limit of 0 (baseline unset, no override) means 'not configured yet', not a literal zero cap - enforcement never suppresses in that state.
