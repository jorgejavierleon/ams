## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Three issues surfaced by code review while implementing KOL-137.4, all in the KOL-137.3 hard/soft email-limit enforcement path. None affect correctness of the currently shipped behavior under normal (non-concurrent, low-volume) conditions, but they're worth hardening/cleaning up: (1) the hard-limit check is a non-atomic check-then-act race under concurrent queued sends, (2) every send after a crossing is already recorded still pays for a redundant Organization lookup plus a full monthly COUNT in both the suppression listener and the soft-limit alert path, and (3) the crossing-tracking helpers on Organization hardcode the current month instead of accepting a $month parameter like their sibling emailSendsCountForMonth(), duplicating the month-key computation and blocking any future use for a non-current month.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Concurrent queued sends for the same organization near its hard limit cannot push the organization's monthly send count past the configured hard limit by more than the number of sends already in flight when the limit was reached
- [x] #2 Sends for an organization that already crossed its hard limit this month do not repeat the Organization lookup and full monthly COUNT on every subsequent send attempt
- [x] #3 Organization::hasCrossedEmailLimitThisMonth() and recordEmailLimitCrossing() accept a $month parameter, consistent with emailSendsCountForMonth(), instead of hardcoding Carbon::now()

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Organization: add a CarbonInterface $month param to hasCrossedEmailLimitThisMonth() and recordEmailLimitCrossing(), delegating the exists-check to a new EmailLimitCrossing::recordedFor(organizationId, type, month) static helper that does not require an Organization instance.
2. Update callers (OrganizationController::edit, SuppressEmailOverHardLimit, RecordEmailSend) to pass Carbon::now() explicitly.
3. RecordEmailSend::raiseSoftLimitAlertIfCrossed: short-circuit via EmailLimitCrossing::recordedFor() before loading the Organization or running the monthly COUNT, once this month's soft-limit crossing is already recorded (safe: soft-limit alerting has no un-cross/resume semantics - firstOrCreate was already a permanent no-op).
4. SuppressEmailOverHardLimit::handle(): after the existing manual-override checks and hardLimit<=0 guard, short-circuit to suppress via hasCrossedEmailLimitThisMonth(HARD) before paying for the COUNT; otherwise wrap the COUNT-then-decide-then-record step in a per-organization Cache::lock()->block() to bound the check-then-act race under concurrent queued sends.
5. Add app/Observers/OrganizationObserver.php (#[ObservedBy] on Organization) that deletes this calendar month's HARD EmailLimitCrossing row when hard_email_limit_override changes, so the new short-circuit cannot leave a stale suppression after an admin raises the limit mid-month (preserves the existing 'raising the hard limit mid-month immediately resumes sending' test).
6. Tests: EmailLimitCrossing::recordedFor() unit coverage; hasCrossedEmailLimitThisMonth/recordEmailLimitCrossing honoring an explicit non-current $month; hard-limit lock mutual-exclusion test (second Cache::lock acquisition fails while held); soft-limit short-circuit test; re-run existing EmailLimitEnforcementTest/OrganizationEmailLimitsTest to confirm no regressions.
7. vendor/bin/pint --dirty --format agent; run the affected Pest files with sail artisan test --compact (not the full suite, per standing project preference).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Verification: vendor/bin/sail php vendor/bin/pint --dirty --format agent -> passed. vendor/bin/sail php vendor/bin/phpstan analyse on the 6 changed files -> 0 errors. vendor/bin/sail artisan test --compact on EmailLimitEnforcementTest (14/14), OrganizationEmailLimitsTest (13/13), EmailVolumeTrackingTest+EmailLimitSettingsManagementTest (11/11), and OrganizationOwnershipTest+OrganizationManagementTest+OrganizationOwnershipSettingsTest+DtSelectOrganizationTest (53/53) all pass. Full suite not run, per standing project preference to defer that until requested.

AC1: added a mutual-exclusion test proving the per-organization Cache::lock used around the hard-limit count-then-decide-then-record step genuinely blocks a second concurrent evaluation while the first holds it (array cache driver backs locks even in tests). This bounds - rather than eliminates - the check-then-act race: sends already past the check when the limit is reached are already in flight (their EmailSend row is only written later, after the real transport call) and cannot be recalled, but the lock prevents an unbounded pile-up of simultaneous stale-count passes.

AC2: added query-count tests proving that once a crossing is recorded, a further send does 3 queries (hard) / 4 queries (soft) total for the whole Mail::send() call, down from needing an extra Organization lookup + monthly COUNT (+ a firstOrCreate round trip) every time. The hard-limit path still loads the Organization (needed for the KOL-137.4 manual-override checks, which must run on every send regardless of crossing state) but skips the COUNT entirely once crossed. The soft-limit path skips the Organization lookup too, since nothing there needs it once crossed.

AC3: hasCrossedEmailLimitThisMonth() and recordEmailLimitCrossing() now take a CarbonInterface $month parameter, consistent with emailSendsCountForMonth(); added a test exercising both methods against an explicit non-current month.

One side effect needed to make AC2's short-circuit safe without breaking the pre-existing 'raising the hard limit mid-month immediately resumes sending' test: added app/Observers/OrganizationObserver.php, which clears this month's recorded HARD crossing whenever hard_email_limit_override changes. Without it, the new short-circuit would keep suppressing forever after a single crossing even if an admin later raised the limit. Covered by two new tests (clears on change, left alone when an unrelated field changes).

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Hardened the KOL-137.3 hard/soft email-limit enforcement path per the three issues surfaced in KOL-137.4 review: (1) SuppressEmailOverHardLimit now short-circuits to suppress once this month's hard-limit crossing is recorded, and otherwise runs its count-then-decide-then-record step inside a per-organization Cache::lock, bounding the concurrent-queued-send race to sends already in flight rather than leaving it unbounded. (2) Both SuppressEmailOverHardLimit and RecordEmailSend's soft-limit alert path now check EmailLimitCrossing::recordedFor() first, skipping the monthly COUNT (and, for the soft path, the Organization lookup too) on every send after the first crossing. (3) Organization::hasCrossedEmailLimitThisMonth() and recordEmailLimitCrossing() now take a $month parameter, matching emailSendsCountForMonth(). Added app/Observers/OrganizationObserver.php to clear a recorded HARD crossing when hard_email_limit_override changes, which the AC2 short-circuit needs to keep the existing mid-month-raise-resumes-sending behavior correct. Verified with pint, phpstan, and the full set of affected Pest files (91 tests); full suite deferred per standing preference.
