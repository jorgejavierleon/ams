## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Three issues surfaced by code review while implementing KOL-137.4, all in the KOL-137.3 hard/soft email-limit enforcement path. None affect correctness of the currently shipped behavior under normal (non-concurrent, low-volume) conditions, but they're worth hardening/cleaning up: (1) the hard-limit check is a non-atomic check-then-act race under concurrent queued sends, (2) every send after a crossing is already recorded still pays for a redundant Organization lookup plus a full monthly COUNT in both the suppression listener and the soft-limit alert path, and (3) the crossing-tracking helpers on Organization hardcode the current month instead of accepting a $month parameter like their sibling emailSendsCountForMonth(), duplicating the month-key computation and blocking any future use for a non-current month.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Concurrent queued sends for the same organization near its hard limit cannot push the organization's monthly send count past the configured hard limit by more than the number of sends already in flight when the limit was reached
- [ ] #2 Sends for an organization that already crossed its hard limit this month do not repeat the Organization lookup and full monthly COUNT on every subsequent send attempt
- [ ] #3 Organization::hasCrossedEmailLimitThisMonth() and recordEmailLimitCrossing() accept a $month parameter, consistent with emailSendsCountForMonth(), instead of hardcoding Carbon::now()
<!-- AC:END -->
