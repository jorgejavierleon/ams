## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Add a 'system role' concept for admin/employee/supervisor — distinct from RolePresenter::PROTECTED_ROLES (dt/saas), which stay fully hidden/uneditable. System roles remain visible and their permissions remain fully editable (per KOL-133), but: they cannot be deleted via the delete action added in KOL-135.2, their name cannot be changed via the rename support added in KOL-135.2, and a 'Restore to default permissions' action resyncs their permissions to the RoleSeeder::EMPLOYEE_PERMISSIONS / SUPERVISOR_PERMISSIONS / ADMIN_PERMISSIONS constants — the permanent source of truth for 'system default', changed only via a code deploy.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. RolePresenter: add SYSTEM_ROLES const (admin/employee/supervisor) plus isDeletable()/isRenameable() helpers centralizing the delete/rename guards.
2. RoleSeeder: add public static defaultPermissionsFor(string $role) mapping a system role name to its ADMIN_PERMISSIONS/EMPLOYEE_PERMISSIONS/SUPERVISOR_PERMISSIONS constant, for restoreDefaults() to resync against.
3. RoleController: destroy() blocks SYSTEM_ROLES too (via isDeletable()); update()'s name validation gets a closure rejecting a name change on a system role (via isRenameable()) while still allowing its permissions to be saved; add restoreDefaults(Role $role) syncing a system role's permissions back to RoleSeeder's default; expose is_system_role on both index() and show() props.
4. Routes: add POST roles/{role}/restore-defaults.
5. Frontend: roles/index.tsx hides the delete row-action for system roles; roles/show.tsx disables the name input (+ hint text) and adds a "Restore default permissions" button + ConfirmDialog for system roles.
6. Lang keys for the rename-blocked validation message, the system-role hint, and the restore-defaults button/dialog/flash copy (en+es).
7. Pest tests: delete/rename blocked for admin/employee/supervisor (permissions still editable when name unchanged), custom roles unaffected, restoreDefaults gating + resync behavior for admin and employee.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implementation: see plan. is_system_role is exposed on both roles/index and roles/show props so the frontend can hide the delete action and lock the name field without a second round trip.

Code review (medium, forked agent) findings and resolutions:
1. Delete-confirmation warning used the org-scoped users_count while destroy() detaches globally across all orgs (roles are shared) - undercounted the real impact. Fixed: added an unscoped `all_users_count` via withCount, used only in the delete-dialog copy; users_count/avatars stay org-scoped for the visible column as before. Added a dedicated Pest test.
2. destroy() called $role->users()->detach() before delete(), redundant since model_has_roles.role_id has cascadeOnDelete() - removed the explicit detach, kept a comment explaining why it's unneeded.
3. RoleSeeder::defaultPermissionsFor()'s match arms duplicate RolePresenter::SYSTEM_ROLES as a second, unsynced source of truth (a mismatch would throw an uncaught 500 route). Documented the coupling with an explicit doc comment cross-reference rather than a bigger refactor, since the sets are guard-gated and currently exact.
4. togglePermission/toggleGroup were duplicated verbatim between roles/create.tsx and roles/show.tsx. Extracted resources/js/hooks/use-role-permission-toggles.ts (state-less, wired to useForm's setData) and reused it in both.
5. The "can this role be deleted/renamed" checks were three ad hoc inline in_array() reassemblies across destroy()/update(). Centralized into RolePresenter::isDeletable()/isRenameable().
6. role-permission-groups.tsx's Checkbox still carried name="permissions[]"/value from the old native-form days; removed since selection is fully controlled.

Verification: 47/47 Pest tests in RoleManagementTest.php passing, RolePresenterTest/RolesPermissionsTest re-run green, pint/tsc/eslint clean. Manual browser walkthrough: system-role delete action hidden from the dropdown, name field locked with hint text on employee/admin/supervisor, permissions still editable, restore-defaults confirm dialog + resync verified end-to-end (added View:Employee to employee role, saved, restored, confirmed it was removed again matching RoleSeeder's default set).
<!-- SECTION:NOTES:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->

Frontend hides the delete action and locks the name field (with a hint + a 'Restore default permissions' button) for system roles on the Roles screens. A follow-up code review caught and fixed a real bug (the delete-confirmation warning undercounted affected users across organizations since roles are shared globally) plus several cleanups (redundant detach() query, duplicated permission-toggle logic between create/edit extracted into a shared hook, ad hoc protected-role checks centralized). Verified with 47 passing Pest tests, pint/tsc/eslint clean, and a full browser walkthrough of the lock/restore UI.
