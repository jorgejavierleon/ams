## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Let an organization's Owner transfer ownership to another user in the same organization, and prevent the organization from ever ending up without an owner.

Transfer must be atomic (the old owner reference and new owner reference change together, never leaving a window with zero or two owners) and restricted to the current owner acting on a target user who belongs to the same organization.

Block deleting or deactivating the current owner's account, and block the owner leaving/being removed from the organization, unless ownership has been transferred to someone else first.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Only the current owner can initiate a transfer, and only to another active user in the same organization
- [x] #2 Transfer is atomic: at no point does the organization have zero or two owners
- [x] #3 Deleting, deactivating, or removing-from-organization the current owner is rejected with a clear error unless ownership was transferred first
- [x] #4 Settings UI exposes an ownership transfer action and shows which user is the current Owner
- [x] #5 Pest tests cover a successful transfer, a rejected transfer to a user outside the organization, and a rejected self-delete/deactivate while still owner

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Action app/Actions/TransferOrganizationOwnership.php: handle(Organization $organization, User $newOwner): void. Validates newOwner belongs to the organization, is_active, and is not already the owner (ValidationException::withMessages, key 'user_id'), then DB::transaction() wrapping $organization->forceFill(['owner_id' => $newOwner->id])->save() (forceFill: owner_id stays out of #[Fillable] per KOL-133.1) plus an activity() log entry, matching app/Actions/Documents/PublishDocument.php's convention. Single-column update is inherently atomic; the transaction wraps the audit log.
2. Guard self-delete: in Settings/ProfileController::destroy(), before Auth::logout()/$user->delete(), throw ValidationException::withMessages(['password' => __('ui.settings.delete.errors.owner_must_transfer')]) when $user->isOwner(). Reuses the password InputError slot already rendered by delete-user.tsx — no frontend change needed there.
3. Guard admin-initiated delete/deactivate: in EmployeeController::destroy() and toggleActive(), after assertEmployee(), flash a 'toast' (type error) and return back() when $employee->isOwner() (destroy) or $employee->isOwner() && $employee->is_active (toggleActive, only blocks the deactivating direction). Matches the existing Inertia::flash('toast', ...) pattern already used for success messages in this controller; these actions have no visible field-level error display, so ValidationException would fail silently.
4. "Remove from organization" (AC #3's third vector): confirmed via research no such action exists anywhere in the codebase today (no endpoint nulls organization_id). Nothing to guard; will note as out-of-scope/inapplicable in the final summary rather than build a new feature.
5. New Settings/OrganizationController (app/Http/Controllers/Settings/OrganizationController.php): edit() renders resources/js/pages/settings/organization.tsx with the org name, current owner (id/name/email or null), the acting user's isOwner() bool, and eligible transfer targets (active users in the same org, excluding the current owner). transfer(Request $request, TransferOrganizationOwnership $action) validates user_id via Rule::exists('users','id')->where('organization_id', ...) (matches OvertimePactController's convention), abort_unless($user->isOwner(), 403), calls the action, flashes a success toast, redirect back(). Authorization for "only the current owner can initiate" is enforced here, not just by route middleware.
6. Routes in routes/settings.php, inside the existing ['auth','role:admin'] org-wide-settings group (same convention as settings-notifications/-documents/-overtime): GET settings/organization -> settings-organization.edit, PATCH settings/organization/ownership -> settings-organization.transfer-ownership.
7. Frontend: resources/js/pages/settings/organization.tsx (useForm + plain <form>, styled like settings/overtime.tsx) showing current Owner; when isOwner is true, a Select of eligible users + Dialog confirmation (styled like delete-user.tsx) submitting the transfer; when false, a read-only hint instead of the form. Add an "Organization" nav entry (Crown icon) to resources/js/layouts/settings/layout.tsx in the existing !isEmployee admin-only group. Run Wayfinder generation (via sail npm run build, vite plugin has formVariants: true) so @/routes/settings-organization and its .form() exist.
8. Lang keys (lang/es/ui.php and lang/en/ui.php): new 'settings.ownership' block (head/title/description/current_owner/no_owner/transfer_button/select_placeholder/confirm_title/confirm_description/not_owner_hint/flash.transferred/errors.*) mirroring the settings.overtime/settings.delete blocks; 'settings.delete.errors.owner_must_transfer'; 'settings.nav.organization'; 'employees.flash.owner_must_transfer_before_delete' / '...before_deactivate' alongside the existing employees.flash block.
9. Tests: extend tests/Feature/OrganizationOwnershipTest.php with TransferOrganizationOwnership coverage (successful transfer swaps owner_id atomically; rejects a target outside the organization; rejects an inactive target; rejects transferring to the current owner) using the existing ownedBy()/isOwner() fixtures. Extend tests/Feature/Settings/ProfileUpdateTest.php with "the organization Owner cannot delete their account" (no 500, user still exists). Add a feature test for the new settings-organization.transfer-ownership route (owner can transfer; non-owner admin gets 403; page shows current owner).

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Added ownership transfer with self-lockout safeguards on top of KOL-133.1's Organization.owner_id/isOwner().

- app/Actions/TransferOrganizationOwnership.php: the single place ownership ever changes (owner_id stays out of #[Fillable] per KOL-133.1's design). Validates the target is active, in the same organization, and not already the owner; wraps the update + an activity log entry in a transaction.
- Guards added at every real removal vector that exists in this codebase: self-service account deletion (Settings/ProfileController::destroy), and admin-initiated employee deletion, deactivation, and edit-form deactivation (EmployeeController::destroy/toggleActive/update). Each rejects with a clear, user-facing error (inline validation error or toast) instead of the unhandled 500 the restrictOnDelete FK previously caused. "Removing from organization" has no existing implementation anywhere in the app, so there was nothing to guard for that vector.
- New Settings > Organization page (Settings/OrganizationController + resources/js/pages/settings/organization.tsx): shows the current Owner, and lets the Owner transfer to another active user in the org via a confirmation dialog. Reachable by the Owner even when they hold no admin role (fixed during code review -- the route was originally gated by role:admin middleware, which would have permanently locked out a non-admin Owner).
- 24 new Pest tests across tests/Feature/OrganizationOwnershipTest.php, tests/Feature/Settings/ProfileUpdateTest.php, tests/Feature/EmployeeManagementTest.php, and the new tests/Feature/Settings/OrganizationOwnershipSettingsTest.php.
- Full manual browser verification of the entire flow (login, view, transfer, blocked delete, blocked deactivate, blocked self-delete, non-owner-admin 403, non-admin-owner access) against the local Sail environment, restoring the dev DB to its original owner afterward.

pint clean, types:check clean, targeted regression suite (179 tests across all touched areas) green. Full suite deferred per project preference until user review.
