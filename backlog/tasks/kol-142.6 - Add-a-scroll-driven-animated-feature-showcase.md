## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Replaced the 6 static alternating FeatureRow calls with a FEATURES data array + FeatureShowcase component. Desktop/tablet (md+): FeatureTextBlock uses framer-motion's useInView (center-of-viewport margin) to track the active feature; FeatureVisualPanel is sticky and crossfades the active visual via AnimatePresence. Below md: original static stacked FeatureRow layout (now without the no-longer-reachable 'reverse' alternation, since that layout is md:hidden and was never visible at md+ anyway).

Code review (medium) surfaced two issues, both fixed: (1) the aria-hidden sticky panel still contained real focusable <Button> elements from the mockup cards — added the 'inert' attribute so they're excluded from the tab order (confirmed via .focus() no longer moving document.activeElement); (2) removed the dead 'reverse' prop/class on FeatureRow.

Verification: npm run types:check clean; eslint on the file clean; vendor/bin/pint --dirty clean; sa test --filter=LandingPageTest passing (5/5, AC6). Browser (chrome-devtools MCP): desktop 1440px screenshots at features 01/02/06 show pin+crossfade working across the range (AC1/AC2); 390px mobile screenshot shows the static stacked fallback, no pin (AC3); decorative panel's button confirmed non-focusable via inert, all 6 text blocks always present in DOM so content stays reachable regardless of scroll position (AC5). AC4: with window.matchMedia('(prefers-reduced-motion: reduce)') forced true via an injected initScript, sampled getComputedStyle(...).opacity across rAF frames during a feature transition — opacity snapped 1→0→1 in a single frame, vs. a smooth multi-frame fade (1, 0.91, 0.84, ... 0, fading back in) under normal motion, objectively confirming the crossfade is instant under reduced motion. The companion CSS dimming (motion-reduce:transition-none on the text blocks) is the standard Tailwind prefers-reduced-motion variant and was confirmed present on the live DOM element, but could not be independently toggled in this sandboxed browser (no OS-level reduced-motion emulation available here) — lower-risk than the JS path since it's Tailwind's built-in media-query mechanism, not custom logic.
