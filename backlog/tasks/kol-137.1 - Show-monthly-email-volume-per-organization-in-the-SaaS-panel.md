## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Walking skeleton for KOL-137: record every outgoing email against the organization it belongs to, and show the monthly count in the SaaS panel. No limits or enforcement yet — this slice only makes usage visible.

Record via a single central listener on Laravel's `Illuminate\Mail\Events\MessageSent` event (confirmed via Laravel docs: this fires for every outgoing message regardless of whether it was sent as a raw Mailable via `Mail::send()`/`Mail::to()` or via a Notification's `mail` channel). This is the same mechanism Laravel Telescope's `MailWatcher` uses to log mail in local dev — inspiration for the single-hook approach, not a dependency; Telescope itself is not installed and has no tenant/limit concept.

**Attributing a send to an organization: use Envelope/MailMessage metadata, not the recipient address.** Users can have mail routed to a `personal_email` that differs from their account email (KOL-62), so matching the "to" address back to a `User` to infer `organization_id` is unreliable. Instead, every Mail/Notification class declares `organization_id` explicitly via `Envelope(metadata: ['organization_id' => $this->organization->id])` (Mailables) or `(new MailMessage)->metadata('organization_id', ...)` (notifications built from `MailMessage`). Confirmed in `vendor/laravel/framework/src/Illuminate/Mail/Mailable.php::buildMetadata()`: metadata is attached to the actual sent message as a `MetadataHeader`, so the central `MessageSent` listener can read `organization_id` straight off the sent message's headers — no separate lookup needed.

This trades away "zero per-class edits" for correctness: each of the ~19 existing Mail/Notification classes (other than the DT-excluded ones below) needs one line declaring its `organization_id`. To stop that from being a silent gap for new mail going forward, add a test that enumerates every class in `App\Mail` and `App\Notifications` (excluding the DT ones) and asserts each declares `organization_id` metadata — a class without it should fail the suite, not fail silently in production.

**Excluded from tracking entirely:** mail sent to Dirección del Trabajo (DT) recipients — `App\Mail\DtAuditNotification` and `App\Mail\SendDtPassword` (dispatched from `App\Http\Controllers\Dt\*`), plus any future mail from that DT namespace. These don't belong to a tenant organization's usage (one goes to the org's own contact address for a regulatory notice, the other to a separate DT-guard user) and must never be counted, limited, or shown against any organization.

Surface the counts on the existing SaaS organizations area (`App\Http\Controllers\Saas\OrganizationController`, `resources/js/pages/saas/organizations/*`): the organization's page should show at least the current and previous calendar month's email counts.

## User stories for manual testing (Gherkin)

```gherkin
Feature: View organization email volume in the SaaS panel

  Scenario: Monthly counts reflect emails actually sent
    Given organization "Acme" has had 12 emails sent to its users this calendar month
    And organization "Acme" had 5 emails sent last calendar month
    When a platform admin opens Acme's page in the SaaS panel
    Then they see 12 emails for the current month
    And they see 5 emails for the previous month

  Scenario: An organization with no email activity shows zero, not an error
    Given organization "NewCo" has triggered no emails this calendar month
    When a platform admin opens NewCo's page in the SaaS panel
    Then they see 0 emails for the current month

  Scenario: Different organizations' counts do not mix
    Given organization "Acme" sent 12 emails this month and organization "Beta" sent 3
    When a platform admin opens Beta's page in the SaaS panel
    Then they see 3 emails for the current month, not 15

  Scenario: Mail sent to a user's personal email still counts for their organization
    Given a user in organization "Acme" has mail routed to their personal_email, not their account email
    When a tracked email is sent to that personal address
    Then it is counted under Acme, because attribution comes from the mail's own organization_id metadata, not the recipient address

  Scenario: DT mail never counts against any organization
    Given a DT audit notification is sent to organization "Acme"'s contact email
    And a DT password-reset email is sent to a Dirección del Trabajo inspector
    When a platform admin opens Acme's page in the SaaS panel
    Then neither of those two emails is included in Acme's count or any other organization's count
```

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Migration: create email_sends (organization_id FK cascadeOnDelete, timestamps, index [organization_id, created_at]). No down().
2. Model App\Models\EmailSend: plain Model (NOT BelongsToOrganization - must stay cross-tenant visible to the SaaS panel, same reasoning as Activity log), organization() belongsTo, HasFactory + factory. Add emailSends(): HasMany to Organization.
3. Listener App\Listeners\RecordEmailSend on Illuminate\Mail\Events\MessageSent: reads X-Metadata-organization_id header off $event->message; if absent, return (this is what naturally excludes DT mail); else create EmailSend. Auto-discovered via app/Listeners convention, no manual registration.
4. Add organization_id Envelope/MailMessage metadata to every tracked class (DtAuditNotification + SendDtPassword excluded, untouched):
   Mail: AuthProfileUpdated (add User $user ctor arg, update UserObserver call site; guard - organization_id nullable), DocumentFullySigned, DocumentSignatureVerificationCode, MarkCreated (guard - organization_id nullable, offline-captured marks).
   Notifications (all already carry an org-scoped model in the constructor except RestDayBalanceAccrued, which uses $notifiable->organization_id with $notifiable typed to User, guarded for nullable): DocumentSignatureRequested, ImportRunCompleted, ImportRunFailed, LeaveApproved, LeaveRejected, LeaveRequestSubmitted, MarkModificationRequested, OvertimePactNearingExpiry, OvertimeRequestApproved, OvertimeRequestRejected, OvertimeRequestSubmitted, ReportExportFailed, ReportExportReady, RestDayBalanceAccrued.
5. OrganizationController@edit: add emailVolume prop {currentMonth, previousMonth} via $organization->emailSends()->whereBetween('created_at', ...)->count().
6. edit.tsx: add an email-volume card showing both counts; add ui.organizations.email_volume.* keys to lang/en/ui.php and lang/es/ui.php.
7. Tests: Pest feature test for the listener (tracked send records a row scoped to org+month, zero-activity org shows 0, two orgs don't mix, personal_email routing still attributes via metadata not recipient, DT mail never recorded); enumeration guard test reflecting app/Mail + app/Notifications directories against a maintained instantiate-and-check map (fails if a new class is added without being accounted for); OrganizationManagementTest additions asserting emailVolume counts on the edit page.
8. Run pint --dirty, filtered Pest tests, npm run types:check.
