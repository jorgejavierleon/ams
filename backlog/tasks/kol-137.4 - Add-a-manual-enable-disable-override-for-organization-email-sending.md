## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Platform admins need a manual kill-switch per organization to immediately stop or resume all of its outgoing email, independent of the automatic soft/hard-limit enforcement in KOL-137.3. This lives in the SaaS panel, next to the email volume card (KOL-137.1) and the limit configuration (KOL-137.2), as a toggle/button on the organization page.

Decided semantics (full override, not a conditional one): disabling blocks every outgoing email for that organization immediately, even if the organization is currently well under both its soft and hard limit. Re-enabling resumes sending immediately, even if the organization is still over its hard limit for the current calendar month — the manual switch unconditionally wins over the automatic block in both directions.

Suppression must behave the same way KOL-137.3 specifies for hard-limit suppression: silent from the end user perspective, no 500s, no queued-job failures — the triggering action in the app completes normally even though its email did not go out.

```gherkin
    Given organization "Acme" has email sending enabled
    When a platform admin opens Acme's page in the SaaS panel
    Then they see a control showing email sending is enabled, with the option to disable it
```

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Migration: nullable boolean `email_sending_override` on organizations (after hard_email_limit_override). null = no manual override (defer to KOL-137.3 automatic enforcement); true = manually force-enabled (bypasses hard limit); false = manually force-disabled (blocks unconditionally).
2. Organization model: add property docblock, Fillable entry, boolean cast, and emailSendingManuallyDisabled()/emailSendingManuallyEnabled() helpers reading the tri-state column.
3. SuppressEmailOverHardLimit listener (single MessageSending hook, event halts on first non-null listener response so this must stay one listener): check the manual override first (false -> suppress, true -> allow and skip hard-limit check entirely), falling through to the existing hard-limit logic only when null.
4. OrganizationController: new toggleEmailSending(Organization) action (PATCH organizations/{organization}/email-sending) flipping override to true when currently false, else false; expose emailSendingEnabled (override !== false) on the edit page.
5. edit.tsx: new card with a Switch bound to emailSendingEnabled, calling router.patch on the new route immediately (preserveScroll/preserveState), matching the employees toggleActive pattern.
6. lang/en+es ui.php: email_sending title/enabled/disabled/hint/flash strings.
7. Regenerate Wayfinder (npm run build) for the new route.
8. Pest: EmailLimitEnforcementTest - disabling suppresses even under limits; re-enabling resumes even over hard limit; toggle persists and reflects on the edit page; null override leaves existing 137.3 behavior untouched.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Tri-state nullable boolean organizations.email_sending_override (null=no manual override, defer to KOL-137.3 automatic hard-limit enforcement; true=force-enabled, bypasses hard limit; false=force-disabled, blocks unconditionally). Checked manually first inside SuppressEmailOverHardLimit (same MessageSending listener as the hard-limit check - Illuminate's event dispatcher halts on the first listener with a non-null response, so a second listener would never run). New PATCH organizations/{organization}/email-sending toggle route, flips to the opposite of 'disabled'. Verified in a real browser against the local dev server (super_admin@example.com) at /saas/organizations/1/edit: toggling off showed 'Deshabilitado' and persisted after reload; toggling back on showed 'Habilitado' with a success toast.

/code-review findings addressed:
- edit.tsx showed the automatic hard/soft-limit alert banners even when a manual override was active, contradicting the actual enforcement state (e.g. a force-enabled org still showed "emails are suppressed"). Fixed: exposed emailSending.overridden (email_sending_override !== null) from the controller and gated both alerts on !emailSending.overridden. Verified in-browser: force-enabling a hard-limit-crossed org now hides the destructive alert.
- toggleEmailSending()'s docblock described the toggle backwards (said never-set -> force-enabled, but null !== false so a fresh org actually toggles to force-disabled first). Corrected the docblock to match the code and the existing test.
Flagged but left out of this ticket's scope (pre-existing in KOL-137.3, not introduced here): the hard-limit check in SuppressEmailOverHardLimit is a non-atomic check-then-act race under concurrent queued sends; every send after a crossing still pays for a fresh Organization lookup + full monthly COUNT in both listeners; hasCrossedEmailLimitThisMonth()/recordEmailLimitCrossing() hardcode Carbon::now() instead of taking a $month param like emailSendsCountForMonth(). Can file as follow-up work if desired.
